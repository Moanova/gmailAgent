## Détails de l'implémentation
- `Checkpoint` (Pydantic) : `run_id`, `etapes_validees`, `syntheses`
  (`dict[str, SyntheseEtape]`), `rapport` ; persistance JSON dans
  `data/checkpoints/<run_id>.json` (`sauvegarder_checkpoint` / `charger_checkpoint`,
  `CheckpointError` si illisible). `data/` est ignoré par git.
- `requete_non_lus` : `is:unread -label:"<libellé>"` construit depuis le registre
  (clé logique `suivi.traite`, libellé résolu/créé via `ResolveurLibelles`) —
  jamais de libellé physique en dur dans le code.
- `lancer_run_tri(run_id=None, *, dry_run=True, client=None, registre=None, dossier_checkpoints=None)` :
  étapes 0–7 du run principal (`workflow.md`) ; étapes 1/3/5 en stubs journalisés
  (implémentées en phases 4/5/6) ; rapport `RapportFinal` ; `dry_run=True` par
  défaut (règle E : aucune écriture Gmail) ; en cas d'erreur : motif journalisé,
  rapport `echec_partiel` + `etape_fautive` persisté, exception relancée (arrêt
  propre). Reprise sur incident : relancer avec le même `run_id` saute les étapes
  déjà checkpointées. Le run vide ne fait aucun appel à l'API Mistral.
- `src/client.py` : `avec_retry` généralisé — prédicat `erreur_retentable` couvrant
  `SDKError` (Mistral) et `HttpError` (Gmail) sur 429/5xx ; 3 tentatives, backoff
  exponentiel base 2 s + jitter.
- Dépendances injectables (client, registre, dossier de checkpoints) pour les tests.
- Itération ruff : 4 lignes > 100 caractères raccourcies.
