## Détails de l'implémentation
- `ClientGmail` (Protocol) : interface minimale `list_labels()` /
  `create_label(name)` — le câblage OAuth/`googleapiclient` arrivera avec
  l'orchestrateur (phase 3) ; la logique de résolution reste découplée et
  testable avec un client factice.
- `CleLogique = str` (alias) : les clés logiques sont des chaînes
  `« groupe.clé »` (`suivi.traite`, …) définies **uniquement** dans
  `config/labels.yaml` ; `RegistreLibelles.iter_cles()` aplatit le registre
  en paires (clé, libellé physique) — utilisé par T2.2 pour les enums
  dynamiques. *(Itération : l'enum `CleLogique` en dur a été supprimé au profit
  du YAML comme source unique — demande utilisateur.)*
- `ResolveurLibelles(registre, client, *, dry_run=False)` :
  - `resoudre(cle) -> labelId` : cache intra-run ; `list_labels` appelé **une
    seule fois** (conception.md §4.4), indexé `name → id` pour toutes les clés ;
  - libellé absent → `create_label`, `labelId` mis en cache, log `info` ;
  - **dry-run** (AGENTS.md §E) : création journalisée (`warning`,
    `dry_run=true`, `action="create_label"`), **aucun appel d'écriture**,
    placeholder déterministe `DRYRUN:<nom>` retourné ;
  - échec de création → `LibelleIrresolubleError` (message avec clé + libellé) ;
  - cache par run structurel : un `ResolveurLibelles` par run (pas de global).
