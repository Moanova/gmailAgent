## Objectif
Incident réel du 10/11/2026 (run `161dd25c-aa42-4ea3-afb5-88691da8ad30`, `--tout --reel`, étape
`lecture_classification`) : `GardeFouAtteintError` au 51e appel d'outil. Le prompt ordonne

vaut 1 + 2×25 = **51 appels > `plafond_appels_outils` = 50**. Le garde-fou a correctement tiré
(filet de sécurité : le 51e appel est refusé avant exécution, run arrêté proprement), mais un
run conforme ne doit jamais l'atteindre — sinon `--tout` s'arrête sur échec alors qu'aucun
libellé n'a été posé (le run suivant retomberait sur les mêmes threads).

## Règles de conception (D58)
- On ne **relève pas** le plafond : tout plafond fixe peut être dépassé par du travail légitime.
  On rend les deux bornes **cohérentes par construction** : le cap de threads recherchés est
  dérivé du budget d'appels, jamais l'inverse.
- Nouveau paramètre `limites.marge_appels_reprise` (défaut 3) : marge d'appels réservée aux
  reprises après erreur d'outil (D56) — distinct de `max_tentatives_synthese` (refus de synthèse).
- `Limites.cap_threads_recherche()` = `min(max_threads_par_run,
  (plafond_appels_outils − 1 − marge_appels_reprise) // 2)`, au moins 1. Invariant :
  `plafond_appels_outils ≥ 2 × cap + 1 + marge_appels_reprise` (pire cas conforme couvert).
  Par défaut : cap = (50−1−3)//2 = **23** → pire cas 1 + 2×23 + 3 = 50 ≤ 50. `--tout` pagine
  (ex. 29 messages → runs de 23 + 6).
- Le budget est aussi **énoncé au modèle** (message utilisateur de chaque conversation :
  « Budget : au plus N appels d'outils… cappée à C threads ») et les prompts des 3 agents
  indiquent que l'aperçu de `get_thread` suffit (`get_message` uniquement si insuffisant).
