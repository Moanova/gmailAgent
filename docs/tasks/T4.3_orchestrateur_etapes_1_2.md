## Plan d'implémentation

1. **Étape 1 (lecture spam)** : `_lancer_spam(...)` (miroir de `_lancer_classification`,
   dépendances injectables) sur la requête `in:spam` via `lancer_conversation(AGENT_SPAM, ...)` ;
   la synthèse est stockée dans le `Checkpoint` (`syntheses["spam"]`) puis l'étape validée.
2. **Étape 2 (validation spam)** : la validation C1–C3 a déjà lieu dans `lancer_conversation`
   (`valider_synthese`) ; un rejet lève → arrêt propre (rapport `echec_partiel`,
   `etape_fautive="lecture_spam"`, déjà en place). Si ok → `_appliquer_libelles_spam` :
   pour chaque message `deplaces`, apposer `suivi.valide-spam` + `suivi.traite` + INBOX et
   retirer SPAM via le resolveur + `api.modifier_libelles` (dry-run = journalisé, règle E ;
   jamais de corbeille). Les ids système `SPAM`/`INBOX` sont des constantes de l'API Gmail,
   distinctes des libellés `Agent/` du registre.
3. **Rapport** : `synthese_spam` renseigné dans le `RapportFinal`.
4. **Tests unitaires** (`test_orchestrator.py`, `TestEtapes12Spam`) : run avec agent spam
   mocké `deplaces` → `modifier_libelles` appelé avec `ajouter=[valide-spam, traite, INBOX]`,
   `retirer=[SPAM]` (dry-run : non exécuté) ; rejet → exception + rapport `echec_partiel` ;
   reprise : `lecture_spam` déjà checkpointée → pas de nouvel appel agent spam ;
   `syntheses["spam"]` persistée. TI `test_agent_classification.py` adapté (scénario spam
   vide préfixé, faux service filtrant `in:spam`).
5. **Vérifications** : `ruff`, `mypy src` (strict), `pytest tests` ; kanban → En revue ;
   commit/push sur demande (règle C).
