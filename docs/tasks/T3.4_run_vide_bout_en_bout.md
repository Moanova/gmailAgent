# Tâche T3.4 : Orchestrateur squelette — run vide de bout en bout (critère de sortie)

## Statut
- [ ] Tests d'intégration mockés
- [ ] Validation dry-run réelle (poste utilisateur, étape 6)
- [ ] Validation utilisateur → « Terminé »

## Objectif
Critère de sortie de la **phase 3** (plan macro) : *un run vide qui tourne de bout
en bout* — d'abord en tests d'intégration mockés, puis en dry-run réel sur la boîte
de l'utilisateur (lecture seule, **aucune écriture Gmail** en phase 3 hors
`migrate-labels --reel` ; le petit périmètre réel avec écritures débutera avec les
phases 4–7, règle E).

## Plan

1. **Tests d'intégration mockés** `tests/integration/test_run_vide.py` : faux client
   Gmail (protocole `ClientGmail` + `search_threads`/`get_thread` simulés).
   Scénarios :
   - `tri` en dry-run → checkpoints écrits, rapport `succes`, 8 étapes validées ;
   - idempotence : 2 runs successifs avec le même `run_id` → étapes non rejouées ;
   - reprise sur incident : checkpoint partiel → run complété sans doublon d'étapes ;
   - `migrate-labels` en dry-run → aucune écriture exécutée.
2. **Validation dry-run réelle** (poste utilisateur, étape 6) :
   `gmailagent tri` (dry-run par défaut) ou `python -m cli tri` → appels de lecture
   réels (`list_labels`/`search_threads`), checkpoint dans `data/checkpoints/`,
   rapport `succes` ; 2 runs successifs (idempotence) ; arrêt + relance avec le même
   `--run-id` (reprise sur incident).
3. **Vérifications** : `ruff check src tests`, `mypy src`,
   `python -m pytest tests/unit tests/integration -v` (`testpaths = ["tests"]` couvre
   déjà `tests/integration`) ; kanban → « En revue » ; commit/push sur `dev` sur
   demande explicite (règle C).
