## Objectif
Incident réel du 10/11/2026 (`gmailagent tri --reel --tout`) : au 3e run
(`aa073eb8-7747-4955-881e-fc38938a7d41`), étape `lecture_classification`, le modèle a émis
`get_thread(threadId="1")` (ID halluciné) ; l'API Gmail a répondu 404 (`threads/1`) et,
`executer_outil` n'étant pas protégé dans la boucle de `lancer_conversation` (`src/agents.py:341`),
le `HttpError` a interrompu tout le run (`run interrompu`, checkpoint `echec_partiel` avec
`etape_fautive=lecture_classification`, arrêt de la boucle `--tout`). Correctif : une erreur
d'exécution d'outil est renvoyée au modèle (ToolMessage `{"erreur": "…"}` + warning
`outil en echec`) pour correction et reprise — jamais un abandon direct du run.

## Règles de conception
- Une erreur d'exécution d'outil (404, argument manquant, etc.) est un **événement de
  conversation**, pas une exception fatale : le modèle la reçoit dans le `ToolMessage` et peut
  réessayer avec un argument valide.
- En cas d'échec, **aucun crédit** dans `threads_lus` / `messages_lus` / `ids_resultats` /
  `ids_corbeille` (la lecture/l'écriture n'a pas eu lieu) : les gardes de complétude continuent de
  s'appliquer normalement.
- Bornes inchangées : `plafond_appels_outils` (50), `max_tentatives_synthese` (3), garde de
  complétude des threads, `plafond_lectures` (100) — un modèle qui persisterait sur un ID invalide
  finit en abandon propre via ces gardes.
- Journalisation : warning `outil en echec` (outil, args bornés, erreur) ; le INFO
  `outil execute` reste réservé aux exécutions réussies (lisibilité du log, D53).
- Aucune écriture Gmail impliquée (règle E inchangée) ; `executer_outil` propage toujours ses
  exceptions hors boucle (contrat inchangé, testé tel quel).
