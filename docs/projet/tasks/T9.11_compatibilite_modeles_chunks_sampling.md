## Origine
Incident réel du 13/11/2026 (`gmailagent tri --reel` avec `MISTRAL_MODEL=mistral-large-latest`, runs
`0403d989-…` puis `c43b9301-…`, fichiers ensuite rétablis par l'utilisateur) :

1. **400 code 3054** « top_p must be 1 when using greedy sampling » au premier appel : le runner envoie
   `temperature=0.0` sans `top_p` (`agent_runner.py:372`) ; le SDK exclut `top_p` du corps quand il est
   `None`. `mistral-small-latest` tolère ; `mistral-large-latest` impose la règle glouton.
2. Après ajout manuel de `top_p=1` (200 OK partout, outils exécutés), `SyntheseInvalideError("contenu
   final de l'agent non textuel")` (`agent_runner.py:481-482`) : ML4 est un modèle à raisonnement
   (`reasoning_effort=high` par défaut, non désactivable), donc `message.content` est une **liste de
   chunks** (`ThinkChunk` + `TextChunk` côté SDK `mistralai` : `str | list[ContentChunk]`), jamais une
   `str`.

## Plan d'implémentation

### Volet 1 — contenu en chunks (`src/gmailagent/agent_runner.py`)
1. Nouveau helper privé `_contenu_texte(content: Any) -> str` : `str` → tel quel ; `list` →
   concaténation des `.text` des chunks dont `type == "text"` (`TextChunk`), en **ignorant** les
   `ThinkChunk` (raisonnement) et tout autre type de chunk ; `None` ou autre → `""`.
2. Message final (remplace `agent_runner.py:481-482`) : `contenu_final = _contenu_texte(message.content)`.
   Le raise « contenu final non textuel » disparaît : si le texte extrait est vide, `extraire_json` lève
   `ExtractionJsonError`, déjà pris en charge par la boucle de refus `_refuser` /
   `max_tentatives_synthese` (abandon propre au-delà) — plus robuste qu'une exception dure.
3. Message assistant rejoué avec tool-calls (`agent_runner.py:~390`, actuellement
   `contenu = message.content if isinstance(message.content, str) else ""`) : utiliser aussi
   `_contenu_texte` (l'historique envoyé au modèle conserve le texte, pas le raisonnement).

### Volet 2 — `top_p` explicite
4. Dans `lancer_conversation`, l'appel `client_mistral.chat.complete(...)` reçoit désormais
   `temperature=<config>` **et** `top_p=<config>` (plus `model`, `messages`, `tools`,
   `response_format`, `max_tokens` inchangés).

### Volet 3 — sampling configurable (`core_config.py`, `config/settings.yaml`)
5. `Modele` gagne deux champs : `temperature: float = Field(ge=0, le=2, default=0.0)` et
   `top_p: float = Field(gt=0, le=1, default=1.0)` (`extra="forbid"` conservé).
6. Validation croisée au chargement (model_validator sur `Modele` ou sur `Parametres`) :
   `temperature == 0` exige `top_p == 1` (règle glouton, code API 3054) → `ParametresInvalidesError`
   explicite au démarrage, au lieu d'un 400 en plein run.
7. `config/settings.yaml`, section `modele:` : documenter `temperature: 0.0` et `top_p: 1.0` avec le
   commentaire « glouton : temperature=0 ⇒ top_p=1 (sinon 400 code 3054) ; mistral-large-latest et
   modèles à raisonnement l'imposent strictement ». Défaut du modèle inchangé (`mistral-small-latest`).
8. `lancer_conversation` lit `parametres_courants().modele.temperature` / `.top_p` (même pattern que
   `limites`), les passe à `chat.complete`, et les journalise dans l'événement `conversation lancee`
   (avec `modele` et `max_tokens`).

### Tests
