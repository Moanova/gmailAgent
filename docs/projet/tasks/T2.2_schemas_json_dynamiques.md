## Contexte technique (vérifié en séance)

### Forme du `response_format` attendue par le SDK mistralai 3.5

```python
{
    "type": "json_schema",
    "json_schema": {
        "name": "<NomDuSchéma>",
        "schema": { ... },        # le JSON Schema lui-même
        "strict": True,
        "description": "...",     # optionnel
    },
}
```

- Modèles SDK : `ResponseFormat` / `JSONSchema` (`mistralai.client.models`), avec
  alias `schema_definition` → sérialisé `schema`.
- Dans les conversations éphémères (pattern retenu, décision D2), le schéma est
  passé via `completion_args.response_format` (champ `response_format` de
  `CompletionArgs`).
- Le SDK fournit `mistralai.extra.utils.response_format.response_format_from_pydantic_model`
  qui applique `rec_strict_json_schema` (set `additionalProperties: false` sur
  tous les objets) — **on n'utilisera pas cette helper** : on construit les
  schémas à la main pour garder le contrôle total (enums dynamiques, exclusion
  de `meta`, nettoyage des `$defs` orphelins).

### Sous-ensemble JSON Schema supporté par Mistral en `strict: true`

La documentation Mistral ne publie pas de liste exhaustive des limitations du
mode strict. En revanche, le SDK lui-même et les retours communautaires
(pydantic-ai#4762, client-python#633) confirment :

- `additionalProperties: false` est requis sur **tous** les objets (le SDK le
  force via `rec_strict_json_schema`) ;
- les schémas issus de Pydantic (`model_json_schema()`) sont le pattern de
  référence supporté (c'est ce que `chat.parse` envoie) ;
- le mode strict de Mistral s'appuie sur une grammaire de schéma (mistral-common,
  Draft 7) — les constructions Pydantic standard (`$defs` + `$ref` locaux,
  `anyOf` pour les optionnels nullable, `enum`, `pattern`, `minLength`,
  `format`) passent.

**Règles retenues pour nos schémas** (sous-ensemble sûr, validé contre le SDK) :

| Élément | Traitement |
| --- | --- |
| `additionalProperties: false` | Sur tous les objets (racine + `$defs`) — déjà garanti par `extra="forbid"` sur les modèles Pydantic |
| Champs optionnels (`erreur`, etc.) | `anyOf: [{type: string}, {type: null}]` + dans `required` (émulation nullable, pattern Pydantic `Optional[str]`) |
| `erreur` avec `default: null` | Le `default` est conservé (annotation, non contraignant) — si rejet API, on le strippera |
| `$defs` + `$ref` locaux | Conservés (pattern Pydantic standard, supporté) |
| `pattern`, `minLength`, `format`, `minimum` | Conservés (présents dans les schémas Pydantic, le SDK les envoie tels quels) |
| `title`, `description` | Conservés (annotations) |

> **Point de vigilance** : si l'API rejette un schéma (400), le premier suspect
> sera `default` ou `format` — on les strippera alors. À valider au premier appel
> réel (phase 3+).

### Architecture retenue : payload agent vs modèle complet

Le contrat d'enveloppe (conception §2.4.2) distingue :

- **payload agent** : produit par le LLM — `{statut, messages, erreur?}` (ou
  `{statut, count, ids, erreur?}`) ;
- **enveloppe complète** : `{statut, messages, erreur?, meta}` — le champ `meta`
  (`run_id`, `etape`, `agent`, `timestamp`) est **injecté par l'orchestrateur**,
  pas produit par le LLM (il ne connaît pas le `run_id`).

**Conséquence** : le schéma JSON envoyé à l'API (via `response_format`) décrit
**uniquement le payload agent** — `meta` est exclu. L'orchestrateur construira
ensuite le modèle Pydantic complet (`SyntheseClassification`, etc.) en ajoutant
`meta`.

### Enums dynamiques depuis le registre

- `categorie` (classification uniquement) : enum = clés logiques du groupe
  `classification` dans `config/labels.yaml`
  (`classification.a-repondre`, `classification.information`,
  `classification.notification`) — **jamais de libellé physique en dur** ;
- `urgence` : enum fixe `["haute", "moyenne", "basse"]` ;
- `statut` : enum fixe par agent (variantes selon conception §2.4.1).

Le pattern `^[a-z0-9-]+\.[a-z0-9-]+$` de `MessageClasse.categorie` (T2.1) est
conforme avec les clés logiques du registre (vérifié en séance).

## Plan d'implémentation

1. **Dans `src/contracts.py`**, ajouter :

   a. **`_schema_payload(cls, *, exclure=("meta",)) -> dict`** (privée) :
      - `copy.deepcopy(cls.model_json_schema())` ;
      - retire les champs exclus (`meta`) de `properties` et `required` ;
      - nettoie les `$defs` orphelins (ex : `Meta` n'est plus référencé) ;
      - retourne le schéma dict.

   b. **`enums Dynamiques`** :
      - `_enum_categories(registre: RegistreLibelles) -> list[str]` : clés logiques
        du groupe `classification` ;
      - `_enum_urgences() -> list[str]` : `["haute", "moyenne", "basse"]` ;
      - `_enum_statut(agent: str) -> list[str]` : variantes par agent.

   c. **`schema_agent(agent: str, registre: RegistreLibelles) -> dict`** (publique) :
      - Sélectionne le modèle (`SyntheseClassification` / `SyntheseSpam` /
        `SyntheseSuppression`) selon `agent` ;
      - Appelle `_schema_payload` ;
      - **Injection des enums dynamiques** dans le schéma :
        - `statut` → `_enum_statut(agent)` (remplace l'enum Pydantic) ;
        - `messages.items.properties.categorie` → `_enum_categories(registre)`
          (classification uniquement) ;
        - `messages.items.properties.urgence` → `_enum_urgences()` ;
      - Retourne le schéma dict prêt à être enveloppé dans `response_format`.

   d. **`response_format_agent(agent: str, registre: RegistreLibelles) -> dict`**
      (publique) :
      - Enveloppe le schéma dans la forme attendue par le SDK :
        `{"type": "json_schema", "json_schema": {"name": ..., "schema": ..., "strict": True}}` ;
      - `name` = nom du modèle (`SyntheseClassification`, etc.).

   e. **Registre par défaut** : `schema_agent` et `response_format_agent`
      acceptent un `registre: RegistreLibelles | None = None` — si `None`,
      chargement via `charger_registre()` (chemin par défaut).

2. **Vérification (smoke, sans appel API)** :
   - Générer les 3 schémas (`classification`, `spam`, `suppression`) ;
   - Vérifier : `additionalProperties: false` sur tous les objets, enums
     dynamiques présents, `meta` absent, `$defs` sans orphelins, tous les
     `$ref` résolus ;
   - Round-trip : un payload JSON conforme au schéma doit valider contre le
     modèle Pydantic complet (avec `meta` injecté).
