## Objectif
`gmailagent tri --tout` : enchaîne les runs tant que `search_threads` renvoie des
threads non lus — rattrapage d'un gros retard en une seule invocation, **sans attendre
le cron** (alternative ponctuelle documentée dans la conception §2.6/§4.1 ; le cron
reste le mode quotidien, phase 10).

## Règles de conception
- Un run = un lot borné (`MAX_THREADS_PAR_RUN = 25` threads) ; `--tout` boucle sur les runs.
- **Plafond de runs par invocation** (garde-fou, ex. 10) : au-delà, arrêt propre avec
  journalisation — jamais de boucle infinie.
- `run_id` **distinct par run** (checkpoints indépendants) ; idempotence inter-runs via
  `is:unread -label:"Agent/traité"` (en `--reel`, les traités sont exclus au run suivant).
- Dry-run par défaut (règle E) : `--tout` seul ne fait aucune écriture Gmail.
- Le rapport final agrège les runs (ou un rapport par run + résumé console).

## Plan d'implémentation
1. `src/cli.py` : option `--tout` sur la sous-commande `tri` ; boucle `while` appelant
   `lancer_run_tri()` avec un nouveau `run_id` à chaque itération, arrêt quand
   `search_threads` ne renvoie plus de thread (exposé via le rapport/la synthèse
   `aucun_message`) ou quand le plafond de runs est atteint.
2. Exposition du « reste à traiter » : la synthèse `aucun_message` ou un compteur de
   threads trouvés par run (déjà journalisé) sert de condition d'arrêt.
3. Tests : boucle bornée (plafond), arrêt quand plus de non lus, `run_id` distincts,
   dry-run sans écriture ; intégration mockée.
4. Vérifications : `ruff`, `mypy src`, `pytest tests -v` ; kanban → En revue ;
   commit/push sur `dev` sur demande explicite (règle C).
